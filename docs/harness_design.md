# Harness 设计方案（已确认并实施，2026-10-12）

## 一、设计依据：开发集数据告诉我们什么

- **单轮的接口问题已经基本解决。** 合法性校验单独开就达到 86%，和全开一样；收尾保护、状态台账单独开也有效，但和合法性校验解决的是同一个问题；购买前审计、需求契约、进展监控单独开都没有可测效果。
- **全开插件后，不可接受的失败只剩 3 题**：检索失败（需求说"LED 夜灯"，gold 是"柱头灯"）、漏看候选、规格选错（小狗"两斤半"，gold 尺码是"XS 建议 2 斤"，下一档 S 是"3–4 斤"）。另有 7 题买了可接受的替代品。剩下的问题主要是**信息不够、需求有歧义**。
- **浪费仍有 20%**，主要是打开没有内容的详情子页（169 次）。
- **由此得到叙事上的衔接**：单轮 harness 修好了接口反馈问题，剩下的失败来自信息不足，这正好引出多轮澄清：该问就问。

## 二、单轮 harness v1：做减法

按三层组织：

| 层 | 组件 | 作用 |
|---|---|---|
| 动作合法性 | 合法性校验 | 动作在当前页无效时拦下，说明原因并列出可点项；文字只差空白或全半角时自动改写成页面原文 |
| 完成完整性 | 停止追问 | 只有环境返回"购买完成"才算完成；agent 没买就停下时追问一次 |
| 上下文 | 页面渲染 | 已有：把环境状态渲染成易读页面 |

**删除**：状态台账、进展监控、购买前审计、需求契约，以及"步数快用完"的提醒。理由是消融实验显示它们没有单独效果，台账还会增加 token。"harness 组件不是越多越好，要用消融决定去留"，这本身也是叙事的一部分。

**可选**：没有内容的详情子页。建议第一遍保持现状，避免利用这份数据集的特性做优化。

**验证**：开发集跑一次 v1，确认和全开持平；然后测试集跑原版和 v1 各一次。

## 三、多轮 ask_shopper

### 1. 构造信息缺失的需求
- 从冻结的约束清单里，把**规格类约束**（颜色、尺码、容量、数量、套餐等）从需求中删掉，由 LLM 改写成自然的"模糊需求"。
- 用规则和 LLM 双重校验被删的信息没有残留，然后冻结。
- 开发集 83 题带规格约束，构造模糊版本；17 题不带，保持原样，作为"不需要问"的**对照组**，用来测过度提问。
- 每道题有三份信息：模糊需求（agent 看）、完整需求（模拟买家看）、被删掉的约束（评测用的"该问什么"标准答案）。

### 2. 模拟买家
- 一个扮演用户的 LLM，只知道完整需求原文，不知道 gold 商品和规格原文，所以回答像真实用户（"要黑色的，29 码"），不会直接报出商品的规格写法。
- 规则：只回答被问到的内容；完整需求里没提的就说"没有特别要求"；不主动透露其他信息；不推荐商品；回答简短。
- 模型：建议 qwen3.7-plus，和 agent（DeepSeek）不同家族，避免"自己配合自己"。论文用的模拟买家是 Qwen3-235B。temperature 设为 0。
- 校验：自动检查泄题（没问就说了）和编造（说了完整需求里没有的内容），并抽样人工看。

### 3. agent 的提问工具
- 新增 `ask_shopper(question)`，原版和插件都有，因为它属于多轮环境本身。
- 每题最多问 3 次。提问不占 35 个环境步数，但计入成本（提问次数和 token）。
- 实现：runner 把完整需求放在 agent 碰不到的地方（agent 没有文件工具），由适配层调用模拟买家。

### 4. 插件的提问策略（新组件，可单独开关）

| 组件 | 什么时候触发 | 做什么 |
|---|---|---|
| ask_hint（按页面触发的提问提示） | agent 在商品详情页，页面上有需要选择的规格项，而需求和对话里都没说明 | 在页面末尾提示："该商品需要选择「尺码」，可选 S/M/L，用户还没说明，可以用 ask_shopper 询问" |
| confirm_gate（购买前确认） | buy_now 前，某个已选规格既不是用户说过的，也没问过用户 | 拦一次："「尺码」选了 M，但用户没说明过，建议先确认" |
| dialogue_ledger（对话台账，可选） | 每次返回页面时 | 附上"已知需求"汇总（模糊需求加每次回答），防止长轨迹里忘了用户的回答 |

单轮 v1 的合法性校验和停止追问也照样保留。

设计要点：
- 提示只在页面上**确实存在未确定的规格项**时才触发，依据是真实页面，有的放矢；对照组用来检验它会不会诱导过度提问。
- confirm_gate 针对的是论文里多轮场景最大的错误类型："没确认细节就购买"，占购买错误的 45.63%。

### 5. 实验设计（每个配置跑一次）

| 组 | 需求 | 能否提问 | harness | 作用 |
|---|---|---|---|---|
| A | 完整 | 否 | v1 | 上限（直接用单轮测试集结果） |
| B | 模糊 | 否 | v1 | 下限：信息缺失让成功率掉了多少 |
| C | 模糊 | 能 | v1 | 模型自己会不会问 |
| D | 模糊 | 能 | v1 + 提问策略 | harness 能补回多少 |

核心指标是**恢复率 = (D − B) / (A − B)**。策略在开发集上调，测试集只跑一次。

### 6. 评测新增
- 提问指标：提问率、平均提问次数、有效提问（问到了被删掉的约束）、冗余提问（问已知信息）、答案利用率（问到的规格最后选对没有）、对照组的过度提问率。
- 模拟买家质量：泄题率、编造率。
- 首错新增两类：**该问没问**（没问就选了规格，而且选错了）、**问了没用**（问到了答案却没照着选）。
- 原有 6 个面板照用；需求满足度按完整需求的约束核对。

## 六、实施记录

### 和设计相比的改动（都在开发集上发现，测试集只跑了一次）

1. **"规格项是否已确定"的判断方法。** 最初的规则是"用户的话里出现过某个选项的片段，就算确定"。冒烟测试发现真实商品的一个规格项常常把颜色、数量、拉力、版本拼在一起（如"【加强版第三代】白色1只装-500拉力"），用户说了"拉力500左右"就会被误判为已确定，颜色其实还没定。改为：按用户的话给每个选项打分，**只有一个选项得分最高**才算确定；并列时算没确定，提示里列出仍然符合的候选。
2. **模拟买家的"选择题"规则。** agent 常把选项列出来让用户挑。冒烟测试里模拟买家替用户挑了需求里没写的尺寸（需求只说"带圆盘的黑色锅"，它答"要 24cm 无盖的"），agent 照此搜了 20 步。改为：用户不直接挑选项，而是用需求里的说法说出要求，需求没写的方面说"你看着选"。同时把"只回答问到的那一项"写得更具体，泄露率从 6% 降到 1%。
3. **新增选择题探针。** 模拟买家上线前的探针原来只有定向问题和无关问题，补上"把真实商品的选项列给它挑"，才发现第 2 条的问题。最终开发集探针：定向 83/83、无关 83/83、选择题 73/73 忠于需求。
4. **评测器修正。** 判断"问题问到了哪些约束"的提示原来把 agent 介绍商品的文字（品类、价格）也算作问到，却漏掉"想要哪个颜色"这类没出现具体值的提问；改为只看问题要用户回答或选择的那一项。

提问策略本身（提示的触发条件、确认只拦一次、提问上限 3 次）在开发集上看完失败案例后没有再调，避免过拟合开发集。

### 结果摘要（测试集，每个配置一次）

- 单轮：原版 51% → v1 89%（严格成功），p = 5e-21。
- 多轮（信息缺失组 164 题，可接受购买）：A 90% / B 53% / C 76% / D 84%，恢复率 C 63%、D 83%；C → D 17 题变好、5 题变差（p = 0.017）。
- 代价：对照组提问率 11% → 40%，成功率没有下降。
- 边界：D 剩下的"该问没问"一半是被删的信息决定买哪件商品、而不是选哪个规格，页面上没有可提示的规格项。下一步可以在搜索结果页按候选商品的差异触发提问。

详细数字见 README。

## 七、按论文的多轮规则复现（2026-10-12）

**为什么要做：**上面的多轮是我们自己搭的（只删规格信息、最多问 3 次、买家只答被问到的那一项），和 ShopSimulator 论文的设置不同，结果不能和论文的多轮成功率（最强模型 38%，SFT+RL 训练后约 35%）放在一起比。论文的多轮不是环境里的开关，而是官方代码里单独的评测程序 `multi_eval`（含模拟买家 `shopper.py`），yyhdbl 的环境副本里没有，所以在我们的运行脚本里照官方代码的规则复现。官方代码没有许可证，提示原文放在 gitignore 的 `third_party/shopsim_official/` 下。

**照官方代码做的部分：**
- 买家提示用官方配置里的版本（比论文附录那版更严格：所有属性确认前一律拒绝下单，并指出缺哪类信息），后面拼上本题完整需求和标准答案的规格选项（官方让买家知道自己要哪个规格；agent 没有文件工具，看不到）。
- 开场：先对买家说"请提供您的购物需求。"，买家的回复就是 agent 收到的第一句话。开场白每题只生成一次并冻结在 `data/multiturn_paper/`，所有组共用，保证配对比较。开发集开场白中位数 18 个字，平均只说出 21% 的约束（158/769）。
- 提问不限次数，但和商店动作一起计入 40 个回合的上限；每条返回后附"轮次: N"。
- 买家只在对话里拒绝，环境层面不拦下单。

**和官方不同的地方：**
- 买家模型用 qwen3.7-plus（官方是 qwen3-235b-a22b-instruct-2507，代理上没有），temperature 0。
- agent 用工具调用，不用官方的"Thought/Action_type"文本格式。官方协议里 agent 每一步不是问买家就是操作商店，只有购买或回合用尽才结束；pi 里模型直接回复文字会结束本轮，所以适配层把这段文字转给买家、把回答作为下一条消息发回。冒烟测试里 agent 大多是这样直接用文字提问的。
- 环境步数上限仍是 35（40 个回合里同时包含提问，很少触及）。
- 官方把一段环境状态文字误拼进了买家的任务描述，这里没有拼。
- 题目用开发集 100 题和 Final-200，不是官方的 1459 题测试集。

**对比组：**
- 原版：基线提示 + 适配层，不加载插件。
- 论文提示词：原版 + 改写成工具版的官方 agent 提示（信息收集、购买前确认、买家说再见后直接买等规则），代表论文"只靠提示词"的做法。这一组是在用户确认的方案之外加的，用来回答"把论文的提示词放进去是不是就够了"。
- 插件全开：基线提示 + 插件（guard、nudge、ask_hint、confirm_gate），插件代码没有为这个设置做任何调整，只是论文模式下不再提示"还能问几次"。

运行方式：

```bash
python3 scripts/make_paper_openings.py --tasks data/dev_ids.json --out data/multiturn_paper/dev_openings.jsonl
```

```bash
python3 runner/run.py --run-name dev_paper_all --paper-openings data/multiturn_paper/dev_openings.jsonl --plugin all --workers 5
```

### 开发集结果（100 题，每组一次，不带 LLM 评审）

| 组 | 严格成功 | 可接受购买（core） | 有购买 | 平均提问 | 平均 LLM 回合 |
|---|---|---|---|---|---|
| 原版 | 43% | 47% | 57% | 7.96 | 27.4 |
| 论文提示词 | 54% | 54% | 62% | 10.30 | 28.3 |
| 插件全开 | 64% | 65% | 70% | 4.19 | 22.9 |

- 原版 → 插件：27 题变好、6 题变差，+21 个点，95% CI [+11, +31]，McNemar p = 0.0003。
- 论文提示词 → 插件：23 题变好、13 题变差，+10 个点，CI [−2, +22]，p = 0.13（100 题上不显著）。
- 原版 → 论文提示词：+11 个点，p = 0.11。
- 插件拦下 210 次无效动作（85 题）；"想打开或选中 gold、但动作无效"这类首错从原版的 20 题降到 0。原版有 545 个环境步（29%）浪费在无效动作上。
- 三组最大的共同失败是没下单，而且几乎都是 40 个回合用完：买家坚持"信息不完整、不能买"，agent 就继续问，或者和买家互相说再见，直到回合耗尽（原版 43 题没买，其中 31 题有互相说再见；插件组 30 题没买，29 题是回合用完）。论文提示词里有"买家说再见就直接买最合适的"这条规则，这一组仍有 38 题没买，说明只靠提示词不够。
- 提问统计要注意：agent 直接回复的文字都会转给买家，所以"再见"之类也算一次提问，原版和论文提示词组的"不必要提问"因此偏高。
- 和论文数字的关系：论文多轮最强模型 38%，训练后的 Qwen3-8B 约 35%。我们的原版已经是 43%，但模型、题目子集、买家模型都不同，只能当参考；主结论看同一设置下三组之间的差距。

### 新组件：收尾和规格选择题（2026-10-12，用户确认先做这两件）

看插件组没下单的 30 题轨迹，主要是两种情况：
1. 互相说再见（约 10 题）：买家说不能买，agent 接受了，双方一直说"再见"直到 40 个回合用完。官方规则其实是买家说再见就立刻买最合适的。
2. 核实僵局（约 14 题）：买家要求确认页面上根本没有的信息（"是不是食品级""有没有滑轮"），这个环境的详情页是空的，agent 只能说确认不了，买家就拒绝；agent 再去搜，搜到回合用完。很多题已经选好了正确的商品和规格，就差下单。

另外，正确商品 92% 的题都打开过，但规格全选对的只有 69%。

**closing（收尾）：**
- 剩余回合不超过 12 时，每条返回附上"还剩 N 个回合，用完还没下单就算失败"。agent 不知道回合上限（官方只显示当前是第几轮）。
- 剩余回合不超过 6（够重新搜索、打开、选规格、下单），或者用户说了再见，就提示"现在必须下单"，并附上看过的商品清单（商品 ID、标题、价格、在哪个搜索词第几页找到的），让它能快速回到最合适的那件。
- 收尾阶段不再做购买前确认，也不再提示去问用户，免得浪费最后几个回合。
- 只提示、不拦截动作。

为什么这是 harness 而不是提示词："买家说再见就直接买最合适的"这条规则论文提示词里就有，但模型到那一步不照做（论文提示词组 38 题没买）。收尾组件在需要的时候把规则送到眼前，并附上执行规则要用的信息（剩余回合、看过的商品），这是写在系统提示开头做不到的。

冒烟测试里发现并改掉的问题：最初的提示只说"必须下单"，用户明确说了"不购买"之后，模型认为下单是违背用户意愿，连续拒绝到回合用完。改为直接引用官方 agent 提示里的任务规则："对话结束时用户仍不满意的，就买最接近用户需求的那一件，不需要用户同意（这是任务要求，不算违背用户）"。

**要注意的一点：**收尾等于在买家拒绝之后仍然下单。论文的打分规则要求最后一定要买，但论文的错误分析里也把"买家拒绝后还下单"算作一种错误。真实产品里收尾应该是"推荐最合适的一款，让用户决定"；这里按论文的打分规则来。

**choice（规格选择题）：**商品页上有用户还没确定的规格时，提问提示里把选项原样加引号列出来（最多 12 个），请 agent 让用户直接挑，而不是泛泛地问"想要什么颜色"。论文设置里用户知道自己要哪个规格，选择题能直接拿到准确答案。购买前确认的提示也相应改成"把可选项原样列给用户"。

两个组件都不放进 "all"，这样"插件全开"仍能和之前的结果直接比较。

**开发集结果（100 题，每组一次）：**

| 组 | 严格成功 | 可接受购买（core） | 有购买 | gold 规格全选对 |
|---|---|---|---|---|
| 原版 | 43% | 47% | 57% | 52% |
| 论文提示词 | 54% | 54% | 62% | 75% |
| 插件全开 | 64% | 65% | 70% | 69% |
| 插件全开 + 规格选择题 | 69% | 73% | 82% | 73% |
| 插件全开 + 收尾 | 79% | 85% | 100% | 79% |
