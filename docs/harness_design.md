# Harness 设计方案（已确认并实施，2026-10-12）

## 一、设计依据：开发集数据告诉我们什么

- **单轮的接口问题已经基本解决。** 合法性校验单独开就达到 86%，和全开一样；收尾保护、状态台账单独开也有效，但和合法性校验解决的是同一个问题；购买前审计、需求契约、进展监控单独开都没有可测效果。
- **全开插件后，不可接受的失败只剩 3 题**：检索失败（需求说"LED 夜灯"，gold 是"柱头灯"）、漏看候选、规格选错（小狗"两斤半"，gold 尺码是"XS 建议 2 斤"，下一档 S 是"3–4 斤"）。另有 7 题买了可接受的替代品。剩下的问题主要是**信息不够、需求有歧义**。
- **浪费仍有 20%**，主要是打开没有内容的详情子页（169 次）。
- **由此得到叙事上的衔接**：单轮 harness 修好了接口反馈问题，剩下的失败来自信息不足，这正好引出多轮澄清：该问就问。

## 二、单轮 harness v1：做减法

按三层组织：

| 层 | 组件 | 作用 |
|---|---|---|
| 动作合法性 | 合法性校验 | 动作在当前页无效时拦下，说明原因并列出可点项；文字只差空白或全半角时自动改写成页面原文 |
| 完成完整性 | 停止追问 | 只有环境返回"购买完成"才算完成；agent 没买就停下时追问一次 |
| 上下文 | 页面渲染 | 已有：把环境状态渲染成易读页面 |

**删除**：状态台账、进展监控、购买前审计、需求契约，以及"步数快用完"的提醒。理由是消融实验显示它们没有单独效果，台账还会增加 token。"harness 组件不是越多越好，要用消融决定去留"，这本身也是叙事的一部分。

**可选**：没有内容的详情子页。建议第一遍保持现状，避免利用这份数据集的特性做优化。

**验证**：开发集跑一次 v1，确认和全开持平；然后测试集跑原版和 v1 各一次。

## 三、多轮 ask_shopper

### 1. 构造信息缺失的需求
- 从冻结的约束清单里，把**规格类约束**（颜色、尺码、容量、数量、套餐等）从需求中删掉，由 LLM 改写成自然的"模糊需求"。
- 用规则和 LLM 双重校验被删的信息没有残留，然后冻结。
- 开发集 83 题带规格约束，构造模糊版本；17 题不带，保持原样，作为"不需要问"的**对照组**，用来测过度提问。
- 每道题有三份信息：模糊需求（agent 看）、完整需求（模拟买家看）、被删掉的约束（评测用的"该问什么"标准答案）。

### 2. 模拟买家
- 一个扮演用户的 LLM，只知道完整需求原文，不知道 gold 商品和规格原文，所以回答像真实用户（"要黑色的，29 码"），不会直接报出商品的规格写法。
- 规则：只回答被问到的内容；完整需求里没提的就说"没有特别要求"；不主动透露其他信息；不推荐商品；回答简短。
- 模型：建议 qwen3.7-plus，和 agent（DeepSeek）不同家族，避免"自己配合自己"。论文用的模拟买家是 Qwen3-235B。temperature 设为 0。
- 校验：自动检查泄题（没问就说了）和编造（说了完整需求里没有的内容），并抽样人工看。

### 3. agent 的提问工具
- 新增 `ask_shopper(question)`，原版和插件都有，因为它属于多轮环境本身。
- 每题最多问 3 次。提问不占 35 个环境步数，但计入成本（提问次数和 token）。
- 实现：runner 把完整需求放在 agent 碰不到的地方（agent 没有文件工具），由适配层调用模拟买家。

### 4. 插件的提问策略（新组件，可单独开关）

| 组件 | 什么时候触发 | 做什么 |
|---|---|---|
| ask_hint（按页面触发的提问提示） | agent 在商品详情页，页面上有需要选择的规格项，而需求和对话里都没说明 | 在页面末尾提示："该商品需要选择「尺码」，可选 S/M/L，用户还没说明，可以用 ask_shopper 询问" |
| confirm_gate（购买前确认） | buy_now 前，某个已选规格既不是用户说过的，也没问过用户 | 拦一次："「尺码」选了 M，但用户没说明过，建议先确认" |
| dialogue_ledger（对话台账，可选） | 每次返回页面时 | 附上"已知需求"汇总（模糊需求加每次回答），防止长轨迹里忘了用户的回答 |

单轮 v1 的合法性校验和停止追问也照样保留。

设计要点：
- 提示只在页面上**确实存在未确定的规格项**时才触发，依据是真实页面，有的放矢；对照组用来检验它会不会诱导过度提问。
- confirm_gate 针对的是论文里多轮场景最大的错误类型："没确认细节就购买"，占购买错误的 45.63%。

### 5. 实验设计（每个配置跑一次）

| 组 | 需求 | 能否提问 | harness | 作用 |
|---|---|---|---|---|
| A | 完整 | 否 | v1 | 上限（直接用单轮测试集结果） |
| B | 模糊 | 否 | v1 | 下限：信息缺失让成功率掉了多少 |
| C | 模糊 | 能 | v1 | 模型自己会不会问 |
| D | 模糊 | 能 | v1 + 提问策略 | harness 能补回多少 |

核心指标是**恢复率 = (D − B) / (A − B)**。策略在开发集上调，测试集只跑一次。

### 6. 评测新增
- 提问指标：提问率、平均提问次数、有效提问（问到了被删掉的约束）、冗余提问（问已知信息）、答案利用率（问到的规格最后选对没有）、对照组的过度提问率。
- 模拟买家质量：泄题率、编造率。
- 首错新增两类：**该问没问**（没问就选了规格，而且选错了）、**问了没用**（问到了答案却没照着选）。
- 原有 6 个面板照用；需求满足度按完整需求的约束核对。

## 六、实施记录

### 和设计相比的改动（都在开发集上发现，测试集只跑了一次）

1. **"规格项是否已确定"的判断方法。** 最初的规则是"用户的话里出现过某个选项的片段，就算确定"。冒烟测试发现真实商品的一个规格项常常把颜色、数量、拉力、版本拼在一起（如"【加强版第三代】白色1只装-500拉力"），用户说了"拉力500左右"就会被误判为已确定，颜色其实还没定。改为：按用户的话给每个选项打分，**只有一个选项得分最高**才算确定；并列时算没确定，提示里列出仍然符合的候选。
2. **模拟买家的"选择题"规则。** agent 常把选项列出来让用户挑。冒烟测试里模拟买家替用户挑了需求里没写的尺寸（需求只说"带圆盘的黑色锅"，它答"要 24cm 无盖的"），agent 照此搜了 20 步。改为：用户不直接挑选项，而是用需求里的说法说出要求，需求没写的方面说"你看着选"。同时把"只回答问到的那一项"写得更具体，泄露率从 6% 降到 1%。
3. **新增选择题探针。** 模拟买家上线前的探针原来只有定向问题和无关问题，补上"把真实商品的选项列给它挑"，才发现第 2 条的问题。最终开发集探针：定向 83/83、无关 83/83、选择题 73/73 忠于需求。
4. **评测器修正。** 判断"问题问到了哪些约束"的提示原来把 agent 介绍商品的文字（品类、价格）也算作问到，却漏掉"想要哪个颜色"这类没出现具体值的提问；改为只看问题要用户回答或选择的那一项。

提问策略本身（提示的触发条件、确认只拦一次、提问上限 3 次）在开发集上看完失败案例后没有再调，避免过拟合开发集。

### 结果摘要（测试集，每个配置一次）

- 单轮：原版 51% → v1 89%（严格成功），p = 5e-21。
- 多轮（信息缺失组 164 题，可接受购买）：A 90% / B 53% / C 76% / D 84%，恢复率 C 63%、D 83%；C → D 17 题变好、5 题变差（p = 0.017）。
- 代价：对照组提问率 11% → 40%，成功率没有下降。
- 边界：D 剩下的"该问没问"一半是被删的信息决定买哪件商品、而不是选哪个规格，页面上没有可提示的规格项。下一步可以在搜索结果页按候选商品的差异触发提问。

详细数字见 README。

## 七、按论文的多轮规则复现（2026-10-12）

**为什么要做：**上面的多轮是我们自己搭的（只删规格信息、最多问 3 次、买家只答被问到的那一项），和 ShopSimulator 论文的设置不同，结果不能和论文的多轮成功率（最强模型 38%，SFT+RL 训练后约 35%）放在一起比。论文的多轮不是环境里的开关，而是官方代码里单独的评测程序 `multi_eval`（含模拟买家 `shopper.py`），yyhdbl 的环境副本里没有，所以在我们的运行脚本里照官方代码的规则复现。官方代码没有许可证，提示原文放在 gitignore 的 `third_party/shopsim_official/` 下。

**照官方代码做的部分：**
- 买家提示用官方配置里的版本（比论文附录那版更严格：所有属性确认前一律拒绝下单，并指出缺哪类信息），后面拼上本题完整需求和标准答案的规格选项（官方让买家知道自己要哪个规格；agent 没有文件工具，看不到）。
- 开场：先对买家说"请提供您的购物需求。"，买家的回复就是 agent 收到的第一句话。开场白每题只生成一次并冻结在 `data/multiturn_paper/`，所有组共用，保证配对比较。开发集开场白中位数 18 个字，平均只说出 21% 的约束（158/769）。
- 提问不限次数，但和商店动作一起计入 40 个回合的上限；每条返回后附"轮次: N"。
- 买家只在对话里拒绝，环境层面不拦下单。

**和官方不同的地方：**
- 买家模型用 qwen3.7-plus（官方是 qwen3-235b-a22b-instruct-2507，代理上没有），temperature 0。
- agent 用工具调用，不用官方的"Thought/Action_type"文本格式。官方协议里 agent 每一步不是问买家就是操作商店，只有购买或回合用尽才结束；pi 里模型直接回复文字会结束本轮，所以适配层把这段文字转给买家、把回答作为下一条消息发回。冒烟测试里 agent 大多是这样直接用文字提问的。
- 环境步数上限仍是 35（40 个回合里同时包含提问，很少触及）。
- 官方把一段环境状态文字误拼进了买家的任务描述，这里没有拼。
- 题目用开发集 100 题和 Final-200，不是官方的 1459 题测试集。

**对比组：**
- 原版：基线提示 + 适配层，不加载插件。
- 论文提示词：原版 + 改写成工具版的官方 agent 提示（信息收集、购买前确认、买家说再见后直接买等规则），代表论文"只靠提示词"的做法。这一组是在用户确认的方案之外加的，用来回答"把论文的提示词放进去是不是就够了"。
- 插件全开：基线提示 + 插件（guard、nudge、ask_hint、confirm_gate），插件代码没有为这个设置做任何调整，只是论文模式下不再提示"还能问几次"。

运行方式：

```bash
python3 scripts/make_paper_openings.py --tasks data/dev_ids.json --out data/multiturn_paper/dev_openings.jsonl
```

```bash
python3 runner/run.py --run-name dev_paper_all --paper-openings data/multiturn_paper/dev_openings.jsonl --plugin all --workers 5
```

### 开发集结果（100 题，每组一次，不带 LLM 评审）

| 组 | 严格成功 | 可接受购买（core） | 有购买 | 平均提问 | 平均 LLM 回合 |
|---|---|---|---|---|---|
| 原版 | 43% | 47% | 57% | 7.96 | 27.4 |
| 论文提示词 | 54% | 54% | 62% | 10.30 | 28.3 |
| 插件全开 | 64% | 65% | 70% | 4.19 | 22.9 |

- 原版 → 插件：27 题变好、6 题变差，+21 个点，95% CI [+11, +31]，McNemar p = 0.0003。
- 论文提示词 → 插件：23 题变好、13 题变差，+10 个点，CI [−2, +22]，p = 0.13（100 题上不显著）。
- 原版 → 论文提示词：+11 个点，p = 0.11。
- 插件拦下 210 次无效动作（85 题）；"想打开或选中 gold、但动作无效"这类首错从原版的 20 题降到 0。原版有 545 个环境步（29%）浪费在无效动作上。
- 三组最大的共同失败是没下单，而且几乎都是 40 个回合用完：买家坚持"信息不完整、不能买"，agent 就继续问，或者和买家互相说再见，直到回合耗尽（原版 43 题没买，其中 31 题有互相说再见；插件组 30 题没买，29 题是回合用完）。论文提示词里有"买家说再见就直接买最合适的"这条规则，这一组仍有 38 题没买，说明只靠提示词不够。
- 提问统计要注意：agent 直接回复的文字都会转给买家，所以"再见"之类也算一次提问，原版和论文提示词组的"不必要提问"因此偏高。
- 和论文数字的关系：论文多轮最强模型 38%，训练后的 Qwen3-8B 约 35%。我们的原版已经是 43%，但模型、题目子集、买家模型都不同，只能当参考；主结论看同一设置下三组之间的差距。

### 新组件：收尾和规格选择题（2026-10-12，用户确认先做这两件）

看插件组没下单的 30 题轨迹，主要是两种情况：
1. 互相说再见（约 10 题）：买家说不能买，agent 接受了，双方一直说"再见"直到 40 个回合用完。官方规则其实是买家说再见就立刻买最合适的。
2. 核实僵局（约 14 题）：买家要求确认页面上根本没有的信息（"是不是食品级""有没有滑轮"），这个环境的详情页是空的，agent 只能说确认不了，买家就拒绝；agent 再去搜，搜到回合用完。很多题已经选好了正确的商品和规格，就差下单。

另外，正确商品 92% 的题都打开过，但规格全选对的只有 69%。

**closing（收尾）：**
- 剩余回合不超过 12 时，每条返回附上"还剩 N 个回合，用完还没下单就算失败"。agent 不知道回合上限（官方只显示当前是第几轮）。
- 剩余回合不超过 6（够重新搜索、打开、选规格、下单），或者用户说了再见，就提示"现在必须下单"，并附上看过的商品清单（商品 ID、标题、价格、在哪个搜索词第几页找到的），让它能快速回到最合适的那件。
- 收尾阶段不再做购买前确认，也不再提示去问用户，免得浪费最后几个回合。
- 只提示、不拦截动作。

为什么这是 harness 而不是提示词："买家说再见就直接买最合适的"这条规则论文提示词里就有，但模型到那一步不照做（论文提示词组 38 题没买）。收尾组件在需要的时候把规则送到眼前，并附上执行规则要用的信息（剩余回合、看过的商品），这是写在系统提示开头做不到的。

冒烟测试里发现并改掉的问题：最初的提示只说"必须下单"，用户明确说了"不购买"之后，模型认为下单是违背用户意愿，连续拒绝到回合用完。改为直接引用官方 agent 提示里的任务规则："对话结束时用户仍不满意的，就买最接近用户需求的那一件，不需要用户同意（这是任务要求，不算违背用户）"。

**要注意的一点：**收尾等于在买家拒绝之后仍然下单。论文的打分规则要求最后一定要买，但论文的错误分析里也把"买家拒绝后还下单"算作一种错误。真实产品里收尾应该是"推荐最合适的一款，让用户决定"；这里按论文的打分规则来。

**choice（规格选择题）：**商品页上有用户还没确定的规格时，提问提示里把选项原样加引号列出来（最多 12 个），请 agent 让用户直接挑，而不是泛泛地问"想要什么颜色"。论文设置里用户知道自己要哪个规格，选择题能直接拿到准确答案。购买前确认的提示也相应改成"把可选项原样列给用户"。

两个组件都不放进 "all"，这样"插件全开"仍能和之前的结果直接比较。

**开发集结果（100 题，每组一次）：**

| 组 | 严格成功 | 可接受购买（core） | 有购买 | gold 规格全选对 |
|---|---|---|---|---|
| 原版 | 43% | 47% | 57% | 52% |
| 论文提示词 | 54% | 54% | 62% | 75% |
| 插件全开 | 64% | 65% | 70% | 69% |
| 插件全开 + 规格选择题 | 69% | 73% | 82% | 73% |
| 插件全开 + 收尾 | 79% | 85% | 100% | 79% |
| 插件全开 + 收尾 + 规格选择题（v2） | 81% | 86% | 100% | 81% |

- 收尾是主要贡献：插件全开 → 加收尾，18 题变好、3 题变差，+15 个点，p = 0.0015；所有题都完成了购买。
- 规格选择题效果小：单独加 +5 个点（p = 0.42），叠在收尾上 +2 个点（p = 0.82），都不显著；收尾之后剩下的规格错误已经不多。
- v2 对比：原版 → v2 +38 个点（42 题变好、4 题变差，p = 5e-9）；论文提示词 → v2 +27 个点（p = 4e-5）。
- v2 的 81% 已经接近开发集单轮"需求一次说全"时 v1 的 86%。剩下 19 题严格失败里，10 题买到了符合需求的替代品（可接受），6 题买错商品，2 题商品对规格错，1 题是标注矛盾题。
- 这些都只在开发集上看过一次，组件参数（12 / 6 个回合）没有调。

## 八、第三版：显式维护任务状态（2026-10-13，task-state 分支）

**为什么做：**v2 的几个组件（提问提示、购买前确认、收尾、规格选择题）都是"看到一种失败、补一个"，背后是同一个原因：用户要什么、哪些已经确认、看过的商品各满足哪几条，全都埋在越来越长的对话里，模型自己记不清，只好靠插件在各个时刻提醒。第三版把这份任务状态从对话里拿出来，单独维护成两张表，提问、下单前核对、收尾都按这两张表来做。

**和 LongHorizon-Harness 的关系：**它把任务状态放在执行之外维护，只用独立核验过的事实更新（Manage-Execute-Audit：管理器维护状态、定下一个子任务，新上下文的执行器执行，只读的核验器核实环境）。它的需求在开始时就从任务描述里一次拆好，用户只在"ask"这条路上补充信息或授权。购物导购里需求本身要靠对话一条条问出来，所以这里的需求表是边问边建的；"只用核验过的事实"在用户这一侧的对应做法是：每一条需求都必须附上用户原话，商品表的每个判断都必须附上页面原文。

**用户拍板：**按第 2.2 节的推荐选项做（"那你新建一个分支吧，在这个分支上开发后续的"）：表由小模型维护；上下文只给系统提示 + 两张表 + 最近 6 步；决策仍由 agent 做，插件在关键时刻提醒；个性化先不放；在开发集上和 v2 比。

### 设计

代码在 `pi-shop/task_state.ts`（运行时 `--state all`，和 `--plugin guard,nudge` 一起用；guard 和 nudge 只管动作在页面上是否有效，和任务状态无关，原样保留）。

| 部分 | 怎么维护 | 只依据什么 |
|---|---|---|
| 需求表 | 用户每说一次话，V4 Flash（不思考）从整段对话重新整理：每条一个方面，状态是已确认 / 用户说无所谓 / 用户说有要求但没说具体；品类、品牌、预算、规格一条都没有时显示"还不知道" | 用户说过的话。每条附原话，原话在用户消息里找不到的条目丢掉 |
| 商品表 | 打开商品详情页时记下页面事实（标题、店铺、类目、价格、属性、规格、看过的详情子页写了什么）；V4 Flash 把每条已确认的需求判成符合 / 不符合 / 页面没写；需求表变了就重判 | 页面上真实出现的文字。证据在页面上找不到就算"页面没写"；预算能换成价格区间时用规则判 |
| 用户态度 | 同一次整理里顺带记下：同意买某件 / 不要某件 / 还要确认 | 用户原话 |

每次调用模型前，把"状态卡"（回合进度、两张表、用户的态度）附在发给模型的最后一条消息后面。这只改发给模型的内容，不改会话记录，每张卡都记在 `state_cards.jsonl`。

按表做的三件事（对应 v2 的组件）：
- **提问（ask）**：刚打开的商品有用户还没定的规格时，把选项原样列出来请 agent 让用户挑（v2 的规格选择题；"定没定"由小模型对照需求表判断，不再用字面匹配）。
- **下单前核对（verify）**：页面上不符合需求、规格没定或选错、用户说过不要这件、需求表还有空缺（预算还不知道、用户说有要求但没说具体）时，每件商品拦一次（v2 的购买前确认，v2 只查规格）。
- **收尾（close）**：回合阈值和 v2 一样（剩 12 轮起提醒，剩 6 轮或用户说再见时必须下单），附的候选清单按商品表排好序（符合的多、不符合的少的在前）。

上下文窗口（`--state-window K`）：K > 0 时只给模型最近 K 步原文，前面换成一句"已省略，信息以状态卡为准"。从某一步的模型消息切开，工具调用和它的结果不会被拆散。

### 冒烟测试里发现并改掉的问题（开发集，2–10 题）

1. **小模型算错预算**：把 64 元判成"在 115–125 元之内"。预算改成规则判断，口径和评测器一致（"以内"是上限，"左右/上下"浮动 20%，"出头"上浮 20%），解析不了的才交给小模型。
2. **证据核对太死**：小模型摘证据常写成"属性：速溶"，而页面原文是"属性：黑茶粉；速溶；……"，被当成找不到、降成"页面没写"。核对时去掉字段名，几个属性拼在一起的分开核对。
3. **把"还不能买"当成否定商品**：论文设置里买家在每个细节都确认前一律说"还不能买"，这不代表商品不对。用户态度分成"不要这件"和"还要确认"，只有前者在排序里降分。
4. **用户的问题一直挂在卡上**：买家问了一句"内胆有没有最新款的推荐"，卡上一直显示"用户在等你回答"，模型被牵着连续 20 多轮去搜"最新款内胆"。改成只在问题刚出现的下一步显示一次。
5. **用户用提问方式说出的条件没记成需求**（"组合装里有卸妆水吗？"），整理提示里补上这一条。
6. 详情子页内容是列表格式，显示成了 `[""]`；改成和适配层一样的拼法，空的显示"空"，和标题一样的显示"和标题一样"。另外加了一条事实标注：某条需求在看过的每件商品页面上都没写时注明，模型就知道这条多半在页面上查不到。

### 和确认方案不一样的地方

- **下单前"用户要先同意买这件"改成可选组件 `consent`，默认不开。**最初的核对按论文官方提示加了这条（"购买前必须向用户确认"），10 题冒烟测试里平均回合从 v2 的 18 涨到 29：一去确认，买家就提新要求，有时要的是页面上根本没有的信息（比如羊毛支数），agent 就一直找到收尾。去掉后核对只按表来。
- **预算用规则判，不用小模型**（见上面第 1 条）。
- **多加一组"保留全部历史 + 状态卡"（`--state-window 0`）。**v2 的历史几乎都能命中缓存（开发集平均每题 18.2 万 prompt token 里 17.1 万是缓存命中，没命中的只有约 1.1 万）。只给最近 6 步时，每一步的开头都在变，缓存基本失效：10 题冒烟测试里 prompt token 总数没降（回合多了），没命中缓存的部分反而是 v2 的十几倍。所以两种上下文都跑，让数据决定窗口值不值得留。

评测器加了两处：第 6 个面板报告维护任务状态的小模型调用量和没命中缓存的 token；新增第 8 个面板（`eval/state_check.py`），检查最后一版需求表准不准（用户说出口的约束有多少进了表、表里的行有多少对得上需求原文的约束、有没有记错）。

### 开发集结果（100 题，每组一次，不带评审，2026-10-13）

| 组 | 严格成功 | 可接受购买 | 有购买 | 平均回合 | 平均提问 | prompt token（没命中缓存） | 维护状态 token |
|---|---|---|---|---|---|---|---|
| v2（全开 + 收尾 + 规格选择题） | 81% | 86% | 100% | 19.3 | 2.8 | 182K（11K） | 0 |
| 第三版，保留全部历史 | 79% | 84% | 98% | 23.2 | 3.2 | 263K（34K） | 14K |
| 第三版，只给最近 6 步 | 77% | 82% | 98% | 22.6 | 2.7 | 116K（87K） | 11K |

- 成功率和 v2 看不出差别：v2 → 保留全部历史，7 题变好、9 题变差（p = 0.8）；v2 → 最近 6 步，9 好 13 差（p = 0.52）。
- 需求表很准：用户说出口的约束 96% 进了表，没有记错的（第 8 个面板）。开场没说的约束被问到的比例 60% → 63%（保留全部历史）。
- 变好的题主要是 v2 没问预算、没问组合装就下单的那类（比如黑茶、粉底液），下单前核对因为"预算还不知道"拦下后去问，问出了真实需求。
- 变差的主要原因是回合变多：平均多 4 轮，触发"现在必须下单"的题从 20 题涨到 32–35 题，被迫买了替代品；"漏看"（正确商品在搜索结果里却没打开）从 1 题涨到 6–7 题。看轨迹，表把所有需求都摆在眼前，模型会去追"页面没写"的那几条：反复看详情子页、把所有条件塞进搜索词，搜出来的结果反而更差。
- 只给最近 6 步：prompt token 少了约三分之一，但没命中缓存的部分是 v2 的 8 倍，成功率也低 2 个点，不值得保留。
- 两个和第三版无关、v2 也有的漏洞：一是只有一个选项的规格没点选就下单（v2 有 8 题这样，其中 7 题买的是对的或可接受的商品，只因为这个不算严格成功）；二是收尾只看回合、不看环境的 35 步上限（第三版有 2 题撞上 35 步没买成）。

### 失败原因和拦截审计（2026-10-13，评测器新增）

评测器原来只说得出第一次出错在哪一步，现在加了失败原因诊断（`eval/diagnose.py`，做法见交接文档第 6 节）：按几条能核对的事实由规则判定，每条需求买的那件和正确商品各自满不满足、用户第几回合说过、正确商品什么时候出现过、规格按用户的话能不能推出来。开发集三组和 v2 测试集的结果：

| 失败原因 | v2 | 第三版，全部历史 | 第三版，最近 6 步 | v2 测试集 |
|---|---|---|---|---|
| 看到过正确商品没回头 | 5 | 8 | 5 | 8 |
| 没问清需求 | 4 | 3 | 4 | 6 |
| 规格没点 | 6 | 3 | 4 | 9 |
| 搜索词不对 | 2 | 0 | 1 | 5 |
| 规格选错 | 1 | 1 | 1 | 0 |
| 标准答案有问题 | 0 | 2 | 2 | 2 |
| 替代品也满足需求 | 0 | 1 | 1 | 2 |
| 系统拦下了正确的购买 | 0 | 0 | 2 | 0 |
| 没买成 | 0 | 2 | 2 | 1 |
| 正确商品难搜到 | 1 | 1 | 1 | 0 |
| 合计（没有严格成功的题） | 19 | 21 | 23 | 33 |
| 附加标签：回合用完被迫下单 | 9 | 14 | 18 | 16 |

- 第三版保留全部历史时，"看到过正确商品没回头"比 v2 多 3 题，和读轨迹的印象一致：表把"页面没写"的需求摆在眼前，模型去追这几条，把早先看到的正确商品丢了。第三版的失败里被迫下单的比例也明显更高。
- "规格没点"在每个版本里都排前面（测试集 9 题），是最便宜的改进点。
- "标准答案有问题"和"替代品也满足需求"加起来，第三版两组各 3 题、v2 测试集 4 题（v2 开发集没有）：买的那件按需求不比正确商品差，或者正确商品本身不满足用户说过的要求，这些不算 agent 的错。
- 拦截审计（第 5 个面板）：下单前核对每拦下一次购买，就看被拦时选的是不是正确商品和全对的规格，也就是放行的话会不会严格成功。两组第三版各拦了 22、23 次购买，其中 17 次本来就是对的（每 4 次只有 1 次拦对）。拦对的那几次救回了 3 题、5 题；拦错的大多只是多花回合，但"最近 6 步"那组有 2 题因此没买成（拦下后去跟用户确认，用户提出页面上查不到的要求，最后买了别的）。
- 状态卡给正确商品标的"用户要"规格，和正确规格一致 95%、98%（第 8 个面板）。错的几次里有一次很典型：用户说"脚比较瘦，平时穿 36 码"，需求表只记了"36 码"，卡上就把"230（36肉脚-37瘦脚）"标成用户要的，agent 把已经选对的 225 改成了 230。

## 九、第四版：前台导购 + 后台买手（2026-10-13，task-state 分支）

**为什么做：**论文多轮设置的痛点是需求要靠对话一点点问出来，而 agent 常常在用户还没点头时就下单。v2 在开发集 100 次下单里，下单前用户最后一句话明确同意的只有 37 次，45 次是用户还在补充需求或提问时就买了。v2 和第三版都是给同一个 agent 加提醒：它既要陪用户聊，又要自己在商店里翻商品，在商店里忙完就直接下单，忘了回去问用户；对话一长，忘了前面看过的好商品；用户问一句页面上没写的信息，就一头扎进商店里找到回合用完。第四版换结构，像真实门店一样分工，规矩只剩一条：用户点头才能下单。

**用户拍板：**"做吧"（按推荐选项：角色分工；主指标是"用户点头后买对"，同时看严格成功；先在开发集跑 20 题看点头率和回合数，没问题再跑全量）。为了比较公平，v2 也补上第四版下单时自带的"只有一个选项的规格自动点上"（`plugin.ts` 的 `spec_fill` 组件，默认不开）。

### 设计

代码在 `pi-shop/roles.ts`，运行时 `--roles`（只用于论文多轮设置，和 `--plugin`、`--state` 不能同时用）；提示在 `prompts/roles_sales.md`（导购）和 `prompts/roles_buyer.md`（买手）。

| 角色 | 看得到什么 | 能做什么 |
|---|---|---|
| 导购（主 agent） | 和用户的对话、候选单 | 直接回复文字（转给用户）；find_products 派买手去找；show_candidates 看候选单，或者填商品ID查这件商品页面上记下的全部内容（都不花回合）；buy 下单 |
| 买手（每次派活新开一个 pi 会话，同一个模型） | 商店页面、这次的找货任务、需求单、已经搜过和看过什么 | 搜索、翻页、打开商品、选规格看价格、看详情页；不能下单，不和用户说话。每次最多 8 个动作 |
| 系统 | — | 整理需求单（第三版的方法，每条附用户原话，原话对不上的丢掉）；把看过的商品按需求单排成候选单（每条判符合 / 不符合 / 页面没写，证据必须能在页面原文里找到，预算按规则判）；按候选单记下的位置回到商品页、点好规格再购买 |

- **唯一的规矩：**用户最后一句话明确同意买这件（整理需求单时顺带判断的用户态度），buy 才放行。回合快用完（剩 6 个回合，或环境步数只剩 6 步）或用户说了再见时，按官方规则兜底：买用户最倾向的那件，不再要求同意；这时导购还只顾着说话，系统替它下单。
- **回合怎么算：**论文协议里 agent 的每个决定算一个回合。分工模式下只算对外的动作：每个商店动作（含被合法性校验拦下的）、每句对用户说的话。导购和买手内部的调用不算回合，另外统计调用次数和 token；导购的模型调用最多 100 次。
- 买手的商店动作先过 v2 的合法性校验（`guardCheck`）。在商品页想打开搜索结果里的另一件时，系统先替它返回上一页；同一件商品的详情页看过一次就记下，不再重复看。
- 连着两次找货，候选单第 1 件都没变，按最新的需求单它也没有和用户要求冲突的地方时，不再派买手去找：剩下的只是页面没写的信息，再找也找不到。

### 第一轮试跑（开发集 20 题）发现的问题

第一轮"用户点头后买对"7/20，和 v2 一样；平均回合 29，比 v2 多 11 个；2 题没买成。看轨迹找到五个原因，改完再跑同样的 20 题：

1. **导购把"页面没写"一条条主动报给用户，用户就不买了。**官方买家在每个属性确认前一律拒绝，导购主动说"颜色页面没写""锁定位置页面没有逐字写出"，买家就要求先确认；而 v2 直接说"页面写着人体定位追踪，符合您要的锁定位置"，买家就同意了。改法：候选单判断时，意思相同或更具体的说法算写了；导购推荐时只说页面上对得上的地方，页面没写的，用户问到再如实说。
2. **导购不肯按官方规则兜底。**用户说了不买，导购就认为不能买，一直聊到回合用完（2 题没买成）。改法：提示里写明官方规则；提示过必须下单后导购还只顾着说话，系统替它买。
3. **反复派买手找同样的东西。**每题找 3–5 次、每次约 7 个回合，而 17/20 题第一次找完正确商品就已经排在第 1。改法：上面那条"不再派买手"的规则。
4. **买手走冤枉路。**在商品页想看另一件时用"回到搜索首页"再重搜，而不是返回上一页；同一个详情页反复看。改法：系统替它返回上一页；看过的详情页记下内容。
5. **导购查不了看过的商品的细节，只能再派买手。**改法：show_candidates 填商品ID，交回这件商品页面上记下的全部内容，不花回合。

第二轮 20 题："用户点头后买对"13/20，严格成功 19/20，平均回合 20.7。

### 开发集结果（100 题，每组一次，不带评审）

| 组 | 严格成功 | 用户点头后买对 | 下单前用户最后一句话：同意 / 没表态 / 刚说完不买 / 没问过 | 平均回合 | 平均提问 | prompt token（没命中缓存） | 系统小模型 token | 触发"现在必须下单" |
|---|---|---|---|---|---|---|---|---|
| v2 | 81% | 33% | 37 / 45 / 13 / 5 | 19.3 | 2.8 | 182K（11K） | 0 | 20 题 |
| v2 + 规格补点 | 85% | 40% | 42 / 33 / 22 / 3 | 22.1 | 3.2 | 221K（14K） | 0 | 27 题 |
| 第四版 | 91% | 61% | 62 / 5 / 33 / 0 | 22.2 | 5.8 | 113K（14K） | 22K | 40 题 |

"用户点头后买对"= 严格成功，并且下单前用户最后一句话明确同意（V4 Pro 判断，`eval/consent.py`）。

- **点头后买对 33% → 61%**：v2 → 第四版 36 题变好、8 题变差，差距明显；比 v2 + 规格补点也是 30 好 9 差。严格成功 81% → 91%（14 好 4 差）；比 v2 + 规格补点 85% → 91%（9 好 3 差），100 题上还看不出来。v2 加规格补点本身两项都看不出差别。
- **不再在用户还没表态时下单：**"没表态"从 45 次降到 5 次，这 5 次全是收尾（用户说再见或回合用完）。第四版 100 次下单里，60 次是系统核对过用户同意的；40 次是按官方规则兜底，其中 33 次用户刚说完不买（21 次用户说了再见，12 次回合快用完）。
- **严格成功的提升从哪来**（失败原因诊断，v2 → 第四版）："规格没点"6 → 0（下单时系统点好规格），"没问清需求"4 → 1（开场没说的约束被问到的比例 60% → 89%），"搜索词不对"2 → 0；"看到过正确商品没回头"5 → 5 没变。
- **token 少了四分之一：**导购看不到商店页面，买手每次新开会话、只带这次任务，一题平均 113K + 系统小模型 22K，v2 是 182K。回合多了约 3 个。
- **代价和还没解决的问题：**
  - 收尾翻倍（20 → 40 题）。用户要确认页面上根本没写的信息时，第四版不会替页面打包票，拿不到同意，只能聊到用户说再见或回合用完再兜底。
  - 导购不接受用户的拒绝：系统在 33 题里拦下 144 次没经同意的下单，其中 129 次买的就是正确商品和全对的规格（放行就会严格成功）；有 1 题因为被拦，最后买了别的。被拦后导购常常再劝一遍，"冗余提问"从 v2 的 49 个涨到 196 个。
  - 买手重复打开同一件商品 122 次（v2 是 47 次）：每次派活都是新会话，导购让它"打开某件看看"时，它要重新搜到再打开。
  - 虚假核验 4 题，其中 3 题是标注矛盾题（正确商品本身就不满足需求原文，比如需求要米白色、正确商品是杏色），另 1 题是品类说法上的分歧（把柱头灯说成 LED 夜灯）。

评测器新增：第 1 个面板报告下单前用户的最后一句话和"用户点头后买对"；第 6 个面板在分工模式下报告用掉的回合（只算对外的动作）、导购和买手各自的调用次数，token 含买手；失败原因诊断识别分工模式的收尾。
