# 秋招叙事：会听话、懂用户的导购 Agent（不改模型，只改 harness）

简历条目见 `docs/resume_draft.md`，设计和实验记录见 `docs/harness_design.md` 第九、十节。下面的数字都来自 ShopSimulator 论文的多轮规则、agent 模型 DeepSeek-V4-Flash、每组跑一次。

## 一句话（30 秒）

在阿里的 ShopSimulator（淘宝商品库的购物 agent 环境）上，我不改模型权重、只改 harness，解决论文点出的两个多轮痛点：agent 没经用户同意就下单；用户画像用不好。两个问题背后是同一件事：agent 分不清手上的信息哪些能拿来做决定。所以整个设计只有一个原则：**每条信息都带出处，按出处决定能不能用**。需求只认用户原话，商品判断只认页面原文，画像按来源分级，下单只认用户明确同意。测试集上，用户点头后买对从 22% 提到 56%；画像场景的严格成功从 66% 提到 81%。整个过程由我自己搭的过程评测驱动：先测评，再定位失败原因，再改，再验证。

## 三分钟讲法

### 1. 场景和问题

ShopSimulator 是阿里的购物 agent 环境，用户需求很细（品牌、型号、规格、预算），商店里有大量相似商品。论文里最难的是多轮：用户一开始只说个大方向，agent 要边问边找，最后买对那一件、规格也要选对。最强的闭源模型在多轮场景只有 29%–38%，加上用户画像后降到 24%–25%，训练过的 8B 模型约 35%。

论文的错误分析给了两个最大的痛点：
- 下单环节的错误里，近八成是没跟用户确认就买，或者用户拒绝了还买；
- 画像场景的错误里，56% 是画像里有的信息没用上，36% 是把画像过度当成硬要求。

我没走训练路线，而是只改 harness：换模型就能用、迭代快、每一步都能解释，同时用评测说明哪些问题 harness 能解决。

### 2. 第一个痛点：没经同意就下单 → 导购 + 买手

- **现象**：我先做的插件版本，严格成功已经到 84%，但"用户点头后买对"只有 36%。对话中用户还在提问它就下单，测试集上有 83 次。
- **原因**：一个 agent 既要陪用户聊，又要在商店里翻商品。我按"最后一次问完用户之后，又在商店里做了几个动作才下单"给插件版的下单分组（不算回合快用完时按规则收尾的单）：

  | 问完用户后又做了几个动作才下单 | 下单时用户没点头 |
  |---|---|
  | 0 个（问完就买） | 0 / 23 |
  | 1–3 个 | 27%（18 / 66） |
  | 4–8 个 | 87%（39 / 45） |
  | 9 个以上 | 100%（24 / 24） |

  原生 agent 也是同样的趋势（8% → 86%）。也就是说，在商店里忙得越久，越不会回去问用户；对话一长，前面看过的好商品和用户说过的话也会丢。这不是哪个插件的问题，是"一个 agent 两头顾"这个结构的问题。
- **做法**：像真实门店一样分工。导购只和用户对话、做决定，看不到商店页面；买手每次在一个新会话里检索、比对商品，不和用户说话、不下单。两边之间只传有出处的事实：需求单的每一条都要能在用户原话里找到，候选单的"符合 / 不符合"都要有页面原文作证据。规矩只有一条：用户明确同意才能下单，回合快用完时按官方规则收尾。这样导购每次做决定时，面对的都是用户刚说的话和一张核对过的候选单，中间隔着的商店动作被压成了一张单子。
- **结果**：用户点头后买对 36% → 56%，对话中没经同意的下单 83 次 → 0 次，严格成功 84% → 90%（原生 agent 是 50% 和 22%），主模型的 token 还少了两成。

### 3. 第二个痛点：画像用不好 → 画像分级

- **现象**：画像场景里，用户只知道一句简版需求，细节记在画像里。第四版能看到画像，严格成功却只有 66%。用户什么都不知道，推荐个差不多的就点头，点头了但买错有 29 道；导购还常把画像里"喜欢的品牌"拿去让买手搜。
- **原因**：先看数据。官方 1,343 道画像测试题里，商品要求只有 18% 写在简版需求里，53% 只出现在画像的"最近搜索词"里；而"喜欢的品牌、颜色"这类长期偏好单独提供的只有 3%，85% 的画像里都有"很喜欢"但这次用不上的牌子。第四版的需求单只认用户原话，画像里的信息进不了排序；导购又分不清哪些画像信息能信。
- **做法**：画像分级，画像是证据，不是命令。系统先照原来整理用户的话，再从画像里挑和这次商品有关的内容：最近搜过的词当成要求，排序、推荐、派买手都要对上；平时的偏好只在几件商品差不多时参考，不拿去搜；和用户的话冲突时听用户的；每一条都要能在画像原文里找到。导购每次只推荐最符合的一件，免得不知情的用户挑错。
- **结果**：严格成功 66% → 81%（36 题变好、7 题变差），用户点头后买对 61% → 72%；画像搜索词里的要求，买到的商品满足率 82% → 91%；点头了但买错 29 → 18 道；拿无关品牌去搜 25 → 15 道。
- **拆开验证（消融）**：每组去掉一处各跑一次；另把画像分级原样重跑一次，量同一配置的波动。最关键的"只写提示词"又拿到测试集上比了一次。

  | 组（严格成功） | 开发集 50 题 | 测试集 200 题 |
  |---|---|---|
  | 第四版 | 64% | 66% |
  | 只写提示词（同样的用法写进导购提示，系统不整理画像） | 76% | 71% |
  | 不分级（平时的偏好也当要求） | 82% | 没跑 |
  | 只用搜索词（平时的偏好不进需求单） | 82% | 没跑 |
  | 画像分级 | 82% / 76%（跑了两次） | 81% |

  开发集上同一配置重跑就差 6 个点，几组分不出来。测试集上分出来了：画像分级比只写提示词多对 31 题、少对 11 题，差距明显；只写提示词比第四版只多 5 个点，看不出差别。所以提升来自系统把最近搜索词整理进需求单、排候选时逐条核对；光在提示词里告诉导购不够，候选单还是只按用户原话排，正确商品排不到前面（正确商品被打开 76% 对 86%）。另外两组看过程：不分级时，买手拿无关牌子去搜的题从 4–5 道涨到 14 道，分级的作用是不被偏好带偏；"偏好当排序参考"这一层看不出作用，偏好干脆不进需求单更好。

### 4. 评测：贯穿始终的那条线

- 不用环境奖励（它有假阴性，比如把"预算左右"当成硬上限）。严格成功按标准答案独立判；需求拆成原子约束（rubric），逐条核对买到的商品。
- 针对痛点设计指标："用户点头后买对"（严格成功，并且下单前用户最后一句话明确同意）；画像场景按约束的信息来源（用户原话 / 画像搜索词 / 长期偏好）分组核对。
- 失败定位：里程碑漏斗（搜到 → 打开 → 规格选对 → 买下）加首个错误动作，再按类型读轨迹找根因。
- LLM 评审按 5 个维度给过程打分，用日志能核对的客观题校准。
- 调参只在开发集上做，测试集每组只跑一次，200 题逐题配对比较。同一配置在开发集 50 题上重跑会差 6 个点，所以开发集只用来找问题、定方向，小于这个的差别不下结论；开发集分不出、又关键的对比（比如"只写提示词"），拿到测试集上确认，测试集上只跑一次，跑完不再改。

**评测本身也要被评测**，这是我觉得最有意思的部分：
- 评审模型只罚"用户说了不买还下单"，不罚"用户还在提问就下单"。加了下单前用户原话的附注和打分上限之后，插件版本的决策质量从 1.62 降到 1.25，和真实情况对上了。
- 模拟用户被问到自己不知道的细节时，会把它们当成必须确认的购买条件，对话拖到回合用完（50 题里 22 题）。补了一句规则后降到 5 题。
- 商店里有同一款商品被不同店铺重复上架，买哪件都会被判错。评测里单独标出来，不去白费力气修。

## 设计思想（能推广到别的场景）

**一个原则：每条信息都带出处，按出处决定能不能用。** 两个痛点看起来不相干，其实是同一个毛病：agent 把不同来源的信息混在一个上下文里，分不清哪些能拿来做决定。整套 harness 就是给每类信息定好出处和用法：

| 信息 | 出处（系统逐字核对） | 能拿来做什么 |
|---|---|---|
| 用户要什么 | 用户原话 | 当要求：排候选、推荐、派买手都要对上 |
| 商品符不符合 | 页面原文 | 判符合 / 不符合；找不到就记"页面没写"，不猜 |
| 画像里最近的搜索 | 平台记下的近期行为 | 当要求，但和用户的话冲突时听用户的 |
| 画像里平时的偏好 | 长期统计 | 不当要求、不拿去搜（消融显示连排序参考都可以不用） |
| 买不买 | 用户最后一句话明确同意 | 才能下单；回合快用完时按官方规则收尾 |

评测也照这个原则：严格成功按标准答案独立判，不用有假阴性的环境奖励；评审打分时附上用户下单前的原话，不让它凭印象认定"用户同意了"。

落到具体做法：
1. **分工，权限分开。** 对话的一方不碰商店，干活的一方不碰用户、不能下单，中间只传有出处的东西。买手每次在新会话里干活、只交回一张候选单，就是业界常说的子 agent 加上下文隔离。适用于所有"一边和人聊、一边操作系统"的 agent，比如客服、订票、运维助手。
2. **规矩少而硬。** 不靠一堆提示词去劝模型"要确认"，而是把"用户点头才能花钱"做成系统层的硬约束：不可撤销的操作必须有人确认。适用于所有会替用户付钱、发消息、改数据的 agent。
3. **画像是证据，不是命令。** 用户原话最可信，其次是最近的行为，最后才是长期偏好；冲突时听用户的。适用于所有带长期记忆的 agent：记忆要分来源、分可信度来用。
4. **评测驱动，评测也要被评测。** 每个改动都对着一个具体问题，验证时看的也是那个问题的数字；评审模型和模拟用户自己也会出错，要单独检查。

## 怎么一步步走到这里（被问"你怎么想到的"时讲）

1. 最早做单轮，插件把严格成功从 51% 提到 89%，但提升主要来自拦下点错的动作，像在修环境接口，故事弱。
2. 转向论文认定的难点：多轮。照官方代码复现了论文的多轮规则，加了几个组件，到 84%。但这些组件像针对失败一个个打补丁，而且评审发现 agent 常在用户拒绝后还下单。
3. 试过把任务状态显式化（需求表 + 商品表），成功率没提升，回合更多。
4. 想清楚真正的痛点是"用户点头后再买，而且要买对"，于是做了导购 + 买手分工。
5. 看了官方的画像数据，发现细节藏在画像的搜索词里、干扰藏在长期偏好里，于是搭了画像场景的评测，定位出两类错误，做了画像分级。
6. 做了消融，拆开看每一处的作用。开发集 50 题重跑就差 6 个点，分不出来；把最关键的"只写提示词"拿到测试集上比，才看清提升来自系统整理需求单，不是提示词。"偏好不能当要求"让买手少走弯路，"偏好当排序参考"这一层没有作用。

失败的尝试也值得讲：第三版没有提升；把画像直接塞进一次整理调用，结果不稳定（用户一回话，画像条目就丢了），改成先整理用户的话、再单独挑画像条目；评审规则第一次改动几乎没效果，加了附注和打分上限才生效；画像分级里"偏好当排序参考"这一层，消融后发现白做了。

## 高频追问和答法

**只用了一个模型、每组只跑一次，靠得住吗？**
开发集和测试集的提升一致（画像分级：开发集 64% → 82%，测试集 66% → 81%）。测试集 200 题逐题对比，36 题变好、7 题变差，差距明显（配对检验 p < 0.001）。同一配置重跑的波动我专门量过：画像开发集 50 题上，重跑差 6 个点，9 题结果翻转。所以开发集只用来找问题、定方向，结论以测试集 200 题的逐题配对为准。最值得补的是换一个模型再跑一次。

**画像分级里每一处各起多大作用？**
做过消融。最关键的是"由系统把最近搜索词整理进需求单、逐条核对"：同样的用法只写进提示词，测试集 71%，画像分级 81%（31 题变好、11 题变差）。"偏好不能当要求"的作用体现在过程上：偏好也当要求时，买手拿无关牌子去搜的题从 4–5 道涨到 14 道。"偏好当排序参考"这一层看不出作用，可以删掉。这些对比先在开发集上做，开发集 50 题重跑就差 6 个点，分不出的我没有硬下结论，最关键的那组拿到测试集上确认。

**这不就是写提示词吗？**
不是，两部分都有对照。下单确认：只改提示词的"论文提示词"组是 58% / 45%（严格成功 / 用户点头后买对），第四版是 90% / 56%；对话中没经同意的下单从 83 次降到 0 次，是系统层拦下的，不是靠提示词劝。画像：同样的用法只写进导购提示、系统不整理画像，测试集 71%，比第四版（66%）只多 5 个点；由系统整理进需求单是 81%。光写在提示词里，候选单还是只按用户原话排，画像里的区分点进不了排序，正确商品排不到前面。

**模拟用户和画像规则是你们自己定的，会不会对自己有利？**
规则照论文设计：用户只知道简版需求，细节在画像里。改过的地方都写明了原因（比如模拟用户会把没想好的细节当成购买条件，那是它的毛病，不是 agent 的）。第四版和画像分级用的是同一套规则、同一批题、同一句开场白。

**画像的搜索词里几乎写着答案，算不算作弊？**
这是数据集故意的设计：论文把需求里的细节挪进了画像。第四版同样能看到画像，却只有 66%，说明难点不在"有没有信息"，而在于分辨：85% 的画像里都有用户很喜欢、但这次用不上的牌子，第四版就被带偏过。画像分级做的正是分清哪些能信。

**为什么不训练模型？harness 和训练是什么关系？**
不是否定训练。harness 不改权重，换模型就能用，迭代快，每一步都能解释，适合先把系统的上限摸清楚。两者也能结合：harness 跑出来的轨迹（尤其是用户点头后买对的那些）可以当训练数据；评测里的"首个错误动作"可以当步级监督信号；"用户点头才下单"可以变成奖励里的约束。

**上线成本和延迟呢？**
画像分级每道题平均不到 1 分钟，主模型约 9 万 token（八成以上命中缓存），另有小模型约 2 万 token 用来整理需求单和排候选。分工之后比插件版本还省 token，因为导购不用背着整页商店信息聊天。

**导购 + 买手和普通的多 agent 有什么区别？为什么不让一个 agent 做完？**
重点不在"多个 agent"，而在两边之间传什么：只传能在原文里找到出处的事实，并由系统按规则做决定（排候选、拦下没经同意的下单、按规格下单）。一个 agent 做完时，对话和商店页面挤在同一个上下文里，它会忘了回去确认，也会把页面上没写的东西当成用户要的。数据上看得很清楚：插件版问完用户马上下单的 23 次全都经过同意，问完又做了 9 个以上动作才下单的 24 次全部没经同意。分工之后，导购做决定时离用户上一句话永远只隔一张候选单。

**官方规则要求最后必须买，那"用户点头才能买"不矛盾吗？**
不矛盾。对话中间用户说不买就不能买；只有用户说再见或者回合快用完时，才按官方规则买最接近的那件。我们把这类收尾单独统计，"用户点头后买对"这个指标就是为了把两种情况分开。

**还剩哪些问题？下一步怎么做？**
剩下最多的是正确商品已经出现在搜索结果里，但标题看不出规格，买手没点开（画像分级测试集还有 24 道）。另外画像里的细节偶尔会让导购选了超出预算的规格。下一步是让候选单也能看到规格层面的信息，以及在画像和用户的话冲突时，规格选择也听用户的。

**LLM 评审靠得住吗？**
评审看不到标准答案，只作参考，主指标是独立判定的严格成功和用户点头后买对。评审先用日志能核对的客观题校准（比如有没有真的下单），发现它漏罚"用户还在提问就下单"之后，加了附注和打分上限，并保证规则只改论文多轮设置，其他设置的评审输入逐字不变。

**换个场景怎么用？**
三条思路都能直接搬：客服或订票 agent 用分工和"用户确认才执行"；个人助理用"画像分级"管理长期记忆，用户刚说的 > 最近行为 > 长期偏好；任何 agent 项目都可以先搭针对痛点的评测，再定位、再改。
