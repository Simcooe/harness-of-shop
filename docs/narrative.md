# 秋招叙事：不改权重，购物 Agent 能走多远

## 一句话

ShopSimulator 原本是后训练场景：论文用 SFT+RL，yyhdbl 用 SFT+GRPO 把 2B 模型训到 62%。我反过来问：**不改模型权重，只改 harness，能做到多少？哪些错误必须靠训练？** 为此我在通用 agent 框架上把购物能力做成可插拔插件，并搭了一套能定位"第一次出错在哪一步"的过程评测。

## 为什么值得做

1. **行业问题**：通用模型变强后，业务侧越来越多是"做 harness 而不是训模型"，但"harness 能替代多少训练"缺少量化回答。yyhdbl 在博客最后专门讨论了"训练 or harness"，没有给出答案。
2. **前人留下的缺口**：yyhdbl 在"当前项目还欠哪些实验"里列了：每题只跑一次、没有置信区间；Action Guard 等 harness 组件没有消融；奖励是序列级，做不了步级信用分配；没做多轮澄清和个性化。论文也指出，训练后多轮场景仍卡在 35% 左右。
3. **天然可比**：yyhdbl 的老师模型就是 DeepSeek V4 Flash，和本项目用的是同一个模型。"把大模型蒸馏成 2B"和"大模型配好 harness 直接干活"可以放在同一把尺子上，比效果、成本和延迟。

## 研究问题

- RQ1：不改权重，harness 能把成功率提高多少？收益来自哪个组件？
- RQ2：harness 的边界在哪？哪些失败 harness 能消除，哪些需要更强的模型或训练？
- RQ3：怎么可靠地评测执行过程，而不只看终局？
- RQ4（扩展）：需求信息不全时，harness 能否让 agent "该问就问"？

## 方法

- **架构**：通用 agent（pi）+ 环境适配层 + 购物插件。插件卸载即退化为原版，每个组件单独开关，能精确量化每个组件的边际收益。这与 LongHorizon-Harness 的思路一致：后端不变，harness 层可替换。
- **设计流程（数据驱动）**：读轨迹 → 归因 → 设计干预 → 正反两向消融 → 保留或删除。
- **过程评测（四层）**：
  - 结果层：严格成功（gold）+ 需求满足度（只从 query 抽取 hard/soft 约束并冻结，允许合理替代品）
  - 过程层：里程碑漏斗；步级首错定位（漏看 gold、误拒 gold、规格错选或漏选、把无效动作当成功、提前停止、仓促购买）；自述一致性（模型说的和环境实际状态是否一致）
  - 干预层：每次拦截或提醒之后，模型是否照做，结果变好还是变坏
  - 元评测：分层抽样人工标注，报告每个自动指标与人工的一致率；多次运行加配对检验

## 已有发现（Final-200 测试集，每个配置跑一次；组件消融在开发集上）

1. **最大的失败不是"模型不会买"，而是环境静默吞掉无效动作。** 原版有 32% 的环境步数是无效动作；29% 的任务以"购买已完成"结束，实际什么都没买。这个行为继承自 WebShop 的文本环境（代码注释原文："If action not valid, perform nothing"），很可能是整个 WebShop 系环境的共性问题，也正是 LongHorizon-Harness 所说"自我报告的进度不可信"在购物场景的具体形态。
2. **同一个模型，插件把严格成功率从 51% 提到 89%**（78 题变好、2 题变差，p = 5e-21），不可接受的失败从 87 题降到 9 题，假装已购买从 29% 降到 0。
3. **harness 要做减法。** 第一版 6 个组件在开发集上做正反两向消融：只开合法性校验就达到全开水平；逐个去掉时看不出任何一个重要，因为收尾保护和状态台账从别的路径缓解了同一个问题。纯提示类组件（需求契约）没有可测效果，结构性组件效果显著，这是"harness 不等于 prompt 工程"的直接证据。据此精简为 2 个组件，效果持平，token 少 30%。
4. **单轮修好之后，剩下的失败来自信息不足，这引出多轮。** 把需求里的规格信息删掉，成功率从 90% 掉到 53%；允许提问后模型自己会问，恢复 63% 的损失；加上提问策略（商品页上有确定不了的规格时提示、购买前确认没依据的规格）恢复 83%，"该问没问"导致的失败从 27 题降到 10 题。代价是需求本来完整的对照组提问率从 11% 升到 40%，但成功率没降。
5. **策略的边界很清楚。** 剩下的"该问没问"一半是被删的信息决定"买哪件商品"而不是"选哪个规格"，页面上没有可提示的规格项。这给出下一步：在搜索结果层面按候选商品的差异触发提问。
6. **模拟器也要被评测。** 冒烟测试里模拟买家替用户挑了需求里没写的尺寸，agent 被误导搜了 20 步。上线前的探针只问中性问题时发现不了，加上"把真实选项列给它挑"的探针才暴露。修复后测试集 213 次回答 0 次泄露、99.5% 忠于需求。
7. **噪声不可忽视。** temperature = 0 时，两次相同的运行也有 22% 的题目成败翻转；多轮对照组里输入完全相同的两组，严格成功也差 9 个点。在这个噪声水平下，yyhdbl 报告的 GRPO 相对 SFT +1.5 个点无法判断真假，所以所有结论都用配对检验。
8. **环境自带的判定有假阴性。** 它把"左右/出头"当硬预算上限，gold 商品略超价时会被判为买错。所以评测器必须独立验证。

## 第二遍要补的实验（按优先级）

- 每个配置跑 3 次，报告均值和区间；与 yyhdbl 的 harness（同一模型）、SFT 60.5%、GRPO 62.0% 同题对比，画效果–成本曲线。
- 基线阶梯：静默 → 最简反馈（只提示"页面未变化"）→ yyhdbl 的 harness → 本插件，拆开"修接口"和"harness 设计"各贡献多少。
- 人工校准：分层抽 50 条左右（含多轮），报告每个自动指标与人工的一致率。
- 多模型：再测 2 个能力不同的模型，看 harness 增益如何随模型能力变化。
- 多轮扩展：搜索结果层面的提问触发；预算类信息缺失；用户画像。
- （投后训练岗时）harness 作为数据飞轮：同一老师模型在本 harness 下采集轨迹，看 gold 轨迹接受率（yyhdbl 是 70.9%）；首错定位标签作为步级监督信号。

## 预期结论的形态

- **能力是"模型 × harness"的系统属性**：同一个模型，harness 决定了它的能力能否稳定兑现。
- **harness 擅长消除的**：协议错误、接口误读、虚假完成、收尾失败。训练也能缓解这些，但 harness 成本低、可解释、立即生效。
- **harness 解决不了的**：规格歧义、近似商品辨别、偏好理解。这些需要更强的模型、训练，或者向用户提问。
- **评测是两条路线的共同基础**：同一套过程评测，既能指导 harness 迭代，也能产出训练需要的步级信号。

## 简历写法

- 基于通用 agent 框架 pi 设计可插拔的购物 harness（卸载即退化为原版）。在 ShopSimulator Final-200 上不改模型权重，把 DeepSeek V4 Flash 的严格成功率从 51% 提升到 89%（配对 McNemar p = 5e-21）；通过正反两向消融把 6 个组件精简为 2 个，效果持平、token 减少 30%。
- 设计多轮澄清策略（按页面触发的提问提示 + 购买前确认）。需求信息缺失时把可接受购买率从 53% 恢复到 84%，恢复完整需求性能的 83%（模型自主提问为 63%），"该问没问"的失败减少 63%；用对照组量化过度提问的代价。
- 搭建 agent 过程评测框架：冻结的需求约束与证据卡核对、购买前核验、自述一致性、步级首错定位、LLM 过程评审（用日志可核对的客观题校准，一致率 85%–100%）、提问质量（有效/冗余/不必要提问、答案利用率、模拟用户泄露与编造率）。发现基线 29% 的任务以"假装已购买"结束、32% 的环境步为无效动作。

## 高频追问

**为什么不训练？**
不是否定训练，而是先回答"不训练能到哪"。业务上 harness 迭代快、成本低、可解释。我在同一测试集上和后训练结果对比，并用评测把失败拆成"harness 可消除"和"需要训练"两类，作为是否值得训练的决策依据。

**提升是不是只是修了环境的 bug？**
基线阶梯实验专门回答这个问题。如果最简反馈就能拿回大部分收益，结论就是"接口反馈设计是第一性的"。这本身就是对 agent 系统设计有价值的发现，和 LongHorizon-Harness "状态必须经过独立验证"的观点一致。

**yyhdbl 也做了 Action Guard，你的贡献是什么？**
他把 Guard 当作训练的配套设施，没有量化它的作用，并且自己把它列为待做实验。我的贡献有三点：把 harness 当作研究对象做受控实验，证明它单独贡献了几乎全部收益、其他组件冗余；建立多次运行加配对检验的评测协议；升级评测本身（首错定位、自述一致性、人工校准）。

**自动评测可信吗？**
分层抽样人工标注，报告每个自动指标与人工的一致率。LLM judge 看不到 gold；评测器也不依赖环境奖励，因为环境判定有假阴性（可以举预算的例子）。

**拿大模型 API 和 2B 训练模型比，公平吗？**
不是比谁更强，而是比同一任务上的效果–成本–延迟前沿，而这正是 yyhdbl 训练小模型的理由（效率）。主结论来自同模型对比：原版对插件、yyhdbl 的 harness 对本插件。跨模型对比只作为决策参考。

**什么时候该训练？**
三种情况：同一类错误在 harness 下仍大量出现；prompt 和规则已经长到难以维护；推理成本必须压低。失败段分析显示，单轮剩余失败集中在规格选择和近似商品辨别；多轮剩余失败里，"问到了但没照着选"几乎没有（答案利用率 99%），主要是"什么时候该问"判断不全，这是策略学习或训练可以发力的方向。

**提问策略会不会让 agent 乱问？**
专门留了需求本来就完整的对照组：提问率从 11% 升到 40%，多是"这个规格可以吗"一类的确认，成功率没有下降。问题还按有效、冗余、不必要分类统计。是否值得多问，取决于业务上一次提问的成本，这个权衡可以通过提示的触发阈值调。

**模拟用户靠谱吗？**
模拟用户只知道完整需求，不知道标准答案；上线前用三类探针（定向、无关、选择题）检查，运行时每次回答都由 LLM 检查是否针对问题、忠于需求、有没有泄露。选择题探针就是因为冒烟测试里发现它替用户挑尺寸才补上的。

**为什么基于 pi，而不是自己写一个 agent 循环？**
"通用 agent 做底座、垂类能力做插件"是现在 Claude Code 加 skills/plugins 的主流形态。插件卸载即退化，才能干净地量化 harness 的边际收益。
